# Issues #247–#264 Experience Completion Design

## Intent

Complete the 18 open P1 experience issues for BookNest by closing verified gaps in the current storefront and admin UI. The intended result is a consistent, accessible experience across the existing browse, cart, checkout, order-tracking, account, and admin flows, without replacing working behavior.

The GitHub issue bodies are the source of truth. Their repeated BN-11 outcome is that core customer and staff tasks work without serious experience failures. The individual issue checklists define the concrete scope.

## Goals

- Establish shared visual tokens and component conventions across storefront and admin (#247–#248).
- Keep home/catalog/book detail data, inventory, empty results, and errors truthful (#249–#251).
- Make cart, checkout, order tracking, and account management clear and reliable (#252–#255, #264).
- Make admin operations understandable across roles and devices (#256).
- Verify mobile, loading, empty, error, success, keyboard, and contrast behavior (#257–#263).
- Preserve backend authorization and server-side price/inventory validation.

## Non-goals and Anti-goals

- Do not replace the current HTML/CSS/JavaScript architecture or perform a broad visual redesign.
- Do not add commerce features, alter payment methods, or change account/role policy beyond what the issue checklists require.
- Do not infer a delivery zone from free-form address text.
- Do not show an order's private delivery address to an unauthenticated visitor; display only data returned by the existing authorized order API and the shipping snapshot needed to explain charges.
- Do not present an API failure as a successful empty result or as confirmed live catalog data.
- Do not close GitHub issues or claim physical-device coverage based only on static tests.

## Current State and Relevant Constraints

- The storefront is served by `index.html`, `book.html`, `main.js`, `book-detail.js`, and `main.css`; admin uses `admin.html`, `admin.js`, and `admin.css`. Shared toast behavior already exists in `assets/toast.js` and `assets/toast.css`.
- Storefront and admin styles have separate token sets. The storefront already has responsive breakpoints, a skip link, visible focus styling, reduced-motion handling, dialogs, catalog filters/pagination, cart quantity controls, and an accessible toast system.
- Catalog hydration requests `/api/books` but silently retains the static catalog on request failure. Catalog search and filters are client-side. The catalog empty message has no recovery action.
- Cart quote requests already display a loading label and disable checkout; failures show unavailable prices. Some browser-storage failures are swallowed.
- Checkout already disables its submit button during order creation, validates fields, preserves the cart on API failure, and uses an idempotency key. It displays subtotal/discount/total but not a server-computed shipping fee.
- The order quote and create-order logic currently calculate total as `subtotal - discount`. `backend/shipping-policy.js` already defines zones, fees, delivery estimates, and the free-shipping threshold, but it is not connected to checkout or order totals. Relational storage constrains `total = subtotal - discount`.
- The API versioning policy declares that adding a required request field or changing the meaning of `total` is breaking and requires a new major version; v1 must remain supported for at least 180 days.
- The account dialog has sign-in, registration, and password-change views, but no dedicated customer-profile edit view. Customer contact data can be captured in checkout and synchronized through the authenticated customer-info API.
- Order tracking currently renders order ID, status, total, and items; the public order projection also returns creation time and payment status/method.
- Admin loaders display text loading/error/empty rows in several tables. Responsive admin navigation scrolls horizontally at narrow widths; admin styles do not define a global visible keyboard-focus treatment.
- `docs/browser-compatibility.md` defines the existing automated matrix: Chrome, Edge, and iPhone 13 / mobile Safari. The existing project design for accessibility work sets WCAG 2.2 AA as the standard.
- The focused toast tests pass. The storefront test command currently cannot load because the workspace lacks the declared `pg` dependency; restore dependencies after this design is approved, then establish a clean baseline before implementation.

## Approaches

1. **Verify issue checklists and implement only confirmed gaps (selected).** Preserve current architecture and visual identity, reuse the existing tokens, API helpers, policy modules, dialogs, and toast system, and add focused tests for the actual missing behavior. This matches the request and limits regression risk.
2. **Rebuild the storefront/admin design system and pages.** Rejected because it expands beyond the issue checklists, duplicates existing work, and creates unnecessary risk to commerce and staff workflows.

## Decisions

- The acceptance boundary is each issue's checklist, WCAG 2.2 AA, and the browser matrix already documented in this repository.
- Preserve the static/demo catalog behavior when the backend is intentionally not configured. When a configured API fails, retain usable fallback content only with an explicit degraded/offline notice and a retry path; never report that failure as a successful empty response.
- Separate successful empty results from loading and errors. Empty catalog and list states should explain what happened and expose a relevant next action (for example reset filters or return to shopping).
- Reuse native controls and dialogs where they already provide keyboard behavior. Add explicit focus management only for custom panels/menus that do not receive native dialog semantics.
- Reuse the shared toast implementation for success, warning, and error feedback. Ensure request failures cannot invoke success feedback, and retain user-entered form data on failure.
- Add a required checkout delivery-zone selection using the existing `inner_city`, `nationwide`, and `remote` policy zones. Use the existing policy values: 20,000 VND inner-city, 30,000 VND nationwide, and 45,000 VND remote; waive shipping at a 300,000 VND subtotal for non-remote zones only.
- Add v2 quote and create-order contracts with a required, validated zone. The current storefront will call v2 for both requests. Keep v1 quote and create-order behavior unchanged during the documented support window; do not silently infer or default the zone for v2.
- Calculate shipping independently on the server for both v2 requests. Return and persist the zone, fee, delivery estimate, and total snapshot; calculate total as `subtotal - discount + shipping fee` on the server. Update relational constraints through a forward migration and keep file/PostgreSQL persistence behavior consistent.
- Show the quote breakdown before confirmation and show order date, state, items, payment state, and shipping zone/fee when the authorized order response includes them. Do not expose recipient address through guest lookup.
- Preserve historical order totals as stored. For orders that predate the shipping snapshot, omit the shipping breakdown rather than inferring a fee or altering the total.
- Keep the selected zone scoped to the current checkout and the created order snapshot; do not add it to customer profile or persistent browser storage.
- Add a profile view to the existing account dialog, using the current authenticated customer-info API and existing password-change flow. Limit fields to already supported customer information and make verification status read-only unless an existing API supports an authorized update.
- Keep error copy safe and actionable; do not add backend business behavior unrelated to issues #253/#264 or to the already documented shipping policy.

## Unchanged Business Invariants

- Server authorization remains authoritative for account and order access. The UI must not broaden guest order lookup beyond the existing order access-code policy.
- Server quotes and order creation remain authoritative for inventory, discounts, shipping, and totals. The same zone and fee snapshot must survive file storage, PostgreSQL persistence, retries, and order lookup.
- Existing v1 clients and previously stored orders retain their prior contract and totals.

## Verification

- Add focused Node tests for the new quote/create-order shipping contract, persistence, invalid zones, fee thresholds, and matching UI breakdown; retain existing order-ownership and idempotency guarantees.
- Add focused storefront/admin tests for empty/loading/error distinctions, retry/reset, preserved inputs, preventing duplicate submission, keyboard focus, and status announcements.
- Run relevant existing tests and the full project test suite after restoring the declared dependencies. Do not treat skipped tests or missing tools as passing.
- Run the existing browser E2E suite where its isolated PostgreSQL and browser requirements are available. Record browser/viewport coverage and limitations.
- Measure contrast for text, controls, states, and focus indicators against WCAG 2.2 AA, record the result, and check the primary shopping flows at desktop and mobile sizes.

## Left to the Builder

- Select token names and map existing styles to them following current CSS conventions.
- Decide the smallest focused test-file placement consistent with the current Node test suite.
- Choose accessible, concise Vietnamese labels and error/retry wording, preserving existing localization style.
- Determine the exact UI treatment for shared loading/error states based on existing component patterns; do not introduce a new UI dependency.
- Review the `/api/v2` route dispatch, forward migration, and storage serialization paths carefully so v1 remains unchanged, old orders retain their historical totals, and new orders use the shipping snapshot consistently.
