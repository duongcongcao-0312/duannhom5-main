# Design: Implement GitHub issues #109–#127

## Intent

Complete the 19 prioritized security, payment, data integrity, operations,
architecture, testing, performance, and documentation issues for BookNest.
The outcome should reduce critical risk first, preserve the current API and
storefront behavior, and provide verifiable evidence for every acceptance
criterion that can be checked from the repository.

## Goals

- Implement and test repository-owned changes for issues #109–#127.
- Follow the user's chosen order: P0, then P1, then P2.
- Reuse existing Node.js modules, PostgreSQL migrations, APIs, test conventions,
  CI workflows, backup tooling, and runbooks where they already meet the issue.
- Keep secrets and personal data out of source, logs, test output, generated
  reports, and this design document.
- Separate locally verifiable code changes from provider/account operations and
  record external acceptance evidence without claiming it was performed.
- Preserve existing API behavior unless an issue requires an explicit,
  documented contract change.

## Non-goals

- Do not rotate/revoke credentials, initiate a real payment, alter production
  data, load-test production, or change provider settings without access and
  explicit operational confirmation.
- Do not paste, print, commit, or ask the user to provide secret values in chat.
- Do not implement unrelated issue #128 or expand scope beyond #109–#127.
- Do not add a new API version unless contract review identifies a breaking
  change that requires one.
- Do not replace the current stack or introduce a new hosting/database provider
  solely to satisfy an issue.

## Anti-goals

- Do not treat a clean Git tree or successful CI run as proof that credentials
  have been revoked or that production payment/backup works.
- Do not claim staging, branch protection, provider backup, restore drills, or
  production transactions were verified without evidence from those systems.
- Do not weaken authentication, authorization, TLS verification, CSP, or
  deployment gates to make tests pass.
- Do not rewrite `server.js` in one unreviewable change or combine module
  extraction with behavioral changes.

## Current state and constraints

- The working tree is clean on `main` at `f878795`, which includes the prior
  #101–#108 work. The user previously chose in-place execution rather than a
  worktree; retain that preference.
- The project is Node.js 20, plain JavaScript, PostgreSQL plus file-backed
  development storage, static HTML/JS, and `node:test`.
- `server.js` is the HTTP entrypoint and still contains routing, request
  validation, response handling, domain operations, and server setup. Existing
  modules already cover authorization, authentication, database adapters,
  order idempotency, coupons, audit, Firebase verification, email, and routing.
- PostgreSQL migrations 001–008 already exist, including relational storage,
  inventory/idempotency support, and privacy-consent records. The consent API
  and storage were added in #101–#108; the current issue #116 is chiefly UI,
  execution semantics, retention, and data-request workflow.
- Existing controls include role policies, order ownership checks, inventory
  transactions, pricing/coupon validation, payment webhooks, idempotency,
  health/readiness endpoints, security headers/CSP, session expiry/revocation,
  audit logging, backup scripts/runbook, OpenAPI, and a PostgreSQL-backed CI
  workflow. These should be verified before adding replacements.
- Render currently describes a single free web service. Its blueprint has
  generic database/admin/email configuration but does not encode complete
  SePay production secrets or a separately managed backup worker. Repository
  changes cannot prove provider secrets, branch rules, storage ACLs, or a
  working restore drill.
- No SePay, Render, production database, or external backup-provider access has
  been confirmed for this task. The implementation plan must assume these
  credentials/permissions are unavailable; never ask for secret values. If an
  authorized provider UI becomes available, perform only explicitly requested,
  low-risk configuration and keep irreversible or financial operations
  subject to a separate confirmation.
- No issue template files were found in `.github/ISSUE_TEMPLATE/`.
- Baseline `npm.cmd test`: 156 tests, 152 passed, 2 failed, 2 skipped. Existing
  failures are `password reset emails a single-use link and replaces the account
  password` (mailer configuration/interface) and `backend APIs - coupons, auth,
  orders and admin workflow` (CORS credentials expectation). The PostgreSQL
  integration and populated-schema upgrade tests skip without their configured
  test database.

## Approaches considered

1. **Priority phases (selected):** finish P0 security/payment/business
   protections first, then P1 data/architecture/release readiness, then P2
   performance and documentation. This matches the user's stated priorities
   and limits exposure before lower-priority optimization.
2. **Dependency-first:** begin with schema and auth foundations, then commerce
   and payments, then operations, followed by refactoring and performance. This
   can reduce implementation rework but delays some P0 controls.
3. **One issue per approval cycle:** request confirmation after each issue.
   This gives the tightest review boundary but adds unnecessary pauses for a
   user who explicitly requested all 19 issues and selected the priority order.

The priority-phased approach is selected. Within each phase, order work by
technical dependency and keep changes small, test-first, and reviewable.
Shared prerequisites (test baseline, secret-safe CI, authorization boundaries,
and data constraints) should be addressed before dependent features.

## Issue-by-issue scope and acceptance criteria

The following captures the user-provided issue scope so implementation does not
depend on earlier conversation context.

### P0

- **#109 — Secrets:** scan all Git history, branches, and tags; rotate/revoke
  exposed API keys, database credentials, and webhook secrets; move secrets to
  environment variables; enable CI secret scanning; verify `.env.example` only
  contains sample data. Acceptance: no valid secret remains committed; exposed
  credentials are revoked; CI detects new secrets; no real credential appears
  in sample configuration.
- **#110 — SePay production:** configure all five `SEPAY_*` variables, sync
  Render/backend config, verify frontend config API, handle missing/invalid
  values, and run a suitable end-to-end payment test. Acceptance: QR shows the
  correct receiver; valid webhook updates the right order; wrong amount/order
  is rejected; missing config blocks deploy; payment test report exists.
- **#111 — Auth/authorization/ownership:** review user/cart/order/admin APIs;
  authenticate at backend; do not trust client `userId`/`role`; check ownership
  on every resource; standardize customer/staff/admin RBAC; audit admin
  operations. Acceptance: user A cannot read/change user B's order; customers
  cannot access admin APIs; role comes from a trusted source; sensitive APIs
  have authorization tests.
- **#112 — Price/coupon/inventory:** calculate price on backend; validate
  coupons server-side; check inventory; reject deleted/discontinued books; use
  transactions/atomic updates against overselling; enforce order state machine.
  Acceptance: client cannot alter price or fabricate discounts; out-of-stock
  orders fail; paid status cannot be set by an untrusted client; concurrent
  orders cannot oversell.
- **#113 — Webhook/idempotency:** verify provider signature/API key; match
  transaction ID, order ID, amount, and receiving account; persist unique
  transaction ID; prevent duplicate/replay; handle wrong/partial/unmatched
  transfers; retain reconciliation history. Acceptance: forged webhook rejected;
  duplicate has one effect; wrong amount never marks paid; reconciliation
  history exists; duplicate, replay, and conflict tests pass.
- **#114 — Session/XSS/CSRF/CORS:** review token/PII storage; evaluate
  `HttpOnly`, `Secure`, `SameSite` cookies where suitable; add CSRF protection
  if cookies are used; review rendered content for XSS; configure CSP/CORS
  allowlist; complete logout, expiry, and revoke. Acceptance: no unhandled
  critical XSS; session expiry/revocation works; CORS is least-privilege; CSRF
  posture matches the auth architecture; session security is tested.

### P1

- **#115 — PostgreSQL:** normalize users/books/orders/order_items/payments/
  coupons; add foreign keys, unique/check constraints, and query-backed indexes;
  transact multi-table order/inventory/payment changes; standardize migrations;
  keep local/staging/production aligned. Acceptance: no orphans; multi-table
  operations are transactional; migrations work on fresh and populated
  databases; tests use a separate database.
- **#116 — Consent/privacy:** connect UI to consent API; let users view/change
  consent; define retention; handle access/update/delete requests; minimize PII
  in session storage/logs; align policy with real behavior. Acceptance: users
  manage consent in UI; backend persists and enforces it; a data-request
  workflow and retention/deletion policy exist; policy contains no unimplemented
  promises.
- **#117 — Backup/restore:** schedule PostgreSQL backups; use independent
  encrypted/access-controlled storage; set retention and failure alerts; write
  restore instructions; drill restore regularly. Acceptance: scheduled backup
  runs; failure alerts; isolated restore and data integrity succeed; RPO/RTO
  and drill record exist.
- **#118 — Architecture:** split routes, controllers, services, repositories,
  middleware, and config; separate auth/books/orders/payments/coupons/privacy;
  keep API behavior stable. Acceptance: `server.js` only initializes/wires the
  app; modules have clear responsibilities; no serious circular dependency;
  regression suite passes; architecture diagram is updated.
- **#119 — REST/OpenAPI:** standardize success/error/status, validation,
  pagination/filtering, and versioning; update OpenAPI; remove stale production
  URLs. Acceptance: API is fully documented; errors are consistent; backend
  validates inputs; OpenAPI validation runs in CI; frontend follows contract.
- **#120 — Unit/integration tests:** cover pricing, coupon, inventory, order
  state, auth/authorization, payment, consent, and PostgreSQL; target 80%
  coverage for critical business logic. Acceptance: core modules have unit
  tests; critical APIs have integration tests; test DB is isolated from
  production; CI fails on test failure or unmet agreed coverage threshold.
- **#121 — Playwright E2E:** test registration/login, search, cart, checkout,
  coupon, payment, tracking, and admin book/order flows. Acceptance: critical
  purchase paths have E2E coverage; payment failure and order ownership are
  tested; tests can run against staging; failures retain diagnostic logs.
- **#122 — CI/CD:** review GitHub Actions; run lint/syntax/tests/migrations/
  secret/dependency scans; require successful checks and configure branch
  protection; auto-deploy staging; approve production deployment. Acceptance:
  PR merge is blocked on CI failure; required checks exist; CI has a test DB;
  production deployment is approval-gated; CI/CD is documented.
- **#123 — Deployment:** provide production-like staging; validate environment;
  finish health/readiness, HTTPS, and database checks; document rollback; assess
  cold start/timeouts/hosting limits; run post-deploy smoke tests. Acceptance:
  staging is stable; missing required config fails preflight; health/readiness
  works; rollback is rehearsed; smoke test passes.
- **#124 — Monitoring:** structured logs, correlation IDs, API latency/error
  rate, database and webhook/backup tracking, alerts, and admin audit. Acceptance:
  dashboards and alerts exist; API/database failures alert; logs avoid
  unnecessary token/password/PII; important actions have audit trail and
  incident runbook.

### P2

- **#125 — Performance:** paginate lists; analyze/optimize PostgreSQL queries,
  indexes, N+1, cache public data safely, optimize images, and consider CDN/
  object storage. Acceptance: no unbounded list response; important queries
  have suitable indexes; cache does not expose PII; images are optimized; a
  before/after report exists.
- **#126 — Load testing:** exercise catalog/search/login/cart/checkout with
  synthetic data at multiple concurrency levels; measure p50/p95/p99, errors,
  CPU/RAM/database connections; validate concurrent transactions and optimize.
  Acceptance: reproducible report and agreed latency/error thresholds; no
  inventory inconsistency; staging meets target or operating limits are
  documented.
- **#127 — Documentation:** update README, architecture, API/database/migrations,
  Firebase, SePay webhook, deploy/backup/restore/rollback/troubleshooting, and
  privacy policy. Acceptance: new contributors can set up from README; docs
  match code; staging/production and operational runbooks exist; no real secret
  is documented.

## Proposed implementation phases

### Phase 1 — P0 critical issues

1. **#109 Secrets:** inspect tracked files and all reachable Git refs/history
   using secret-scanning tools configured not to print matched values; add
   push/PR secret scanning and safe `.env.example` assertions. Any discovered
   credential is recorded only by file/ref and fingerprint/redacted category.
   Rotation/revocation is an operator/provider action; treat it as pending until
   the owner confirms revocation in the provider.
2. **#114 Session/browser security:** verify token storage, expiry/revocation,
   CORS allowlist, CSP, safe rendering, and CSRF posture. Add only missing
   protections and focused tests. Keep bearer-token architecture unless evidence
   justifies cookie migration; do not add cookie CSRF machinery without cookies.
3. **#111 Identity and ownership:** map sensitive routes and test each public,
   customer, staff, and admin boundary. Derive identity/role from verified
   server session; close ownership gaps and ensure admin audit records.
4. **#112 Pricing/inventory/state:** verify backend-authoritative totals,
   coupon constraints, product availability, atomic stock reservation, and
   order/payment state transitions; add missing focused concurrency/business
   tests.
5. **#113 Webhook/idempotency:** verify provider authentication, transaction
   uniqueness, amount/order/account matching, duplicate/replay/conflict
   handling, and reconciliation history. Add database constraints/migrations
   only where current storage is insufficient.
6. **#110 SePay production:** validate all required production configuration
   fail-closed, document Render secret names, and test config/webhook paths with
   synthetic or provider sandbox data. Do not execute real production charges.
   A live end-to-end report remains externally blocked until the operator
   configures provider secrets and approves a controlled transaction.

### Phase 2 — P1 important issues

1. **#115 PostgreSQL:** review schema and migrations, constraints, transactions,
   indexes, and fresh/upgrade migration coverage. Do not rewrite stable schema
   just for normalization; only add evidence-backed constraints/indexes.
2. **#116 Privacy:** connect the account UI to consent APIs, enforce purpose
   state where data use is optional, define retention and data-request workflow,
   and align the policy with implemented behavior. Keep legally required order
   records distinct from optional purposes.
3. **#117 Backup/restore:** harden repository-owned scheduler/configuration,
   encryption/integrity and alerting capabilities as feasible, document
   independent storage setup, and test restore in isolation. Provider scheduler,
   storage permissions, and a real drill require operator evidence.
4. **#118 Architecture:** extract route/controller/service concerns from
   `server.js` incrementally, preserving the existing public API and testing
   after every extraction. Keep the entrypoint focused on configuration,
   dependency wiring, and server lifecycle.
5. **#119 API/OpenAPI:** align validation, error/status shapes, pagination, and
   OpenAPI with actual routes; add machine validation in CI. Keep current `/api`
   contract and establish a versioning/deprecation policy rather than adding a
   redundant version prefix.
6. **#120 Tests:** add tests to high-risk domain boundaries and raise coverage
   only for explicitly selected business modules to at least 80%; preserve
   current global CI gates unless a measured change is approved.
7. **#121 E2E:** add Playwright flows using local/test services and synthetic
   accounts; capture failure artifacts with secret-safe redaction. Staging
   execution requires a configured environment and safe test data.
8. **#122 CI/CD:** add secret/dependency/OpenAPI/migration checks and define
   required check names and environment approvals in repository configuration
   where possible. GitHub branch protection/rulesets are account-level settings
   and require repository-admin permissions.
9. **#123 Deployment:** strengthen preflight, health/readiness, rollback,
   cold-start and smoke-test documentation/configuration. Actual staging
   stability and rollback drill require deployment access and run evidence.
10. **#124 Monitoring:** use existing structured logs/request IDs/audit and
    health checks; add missing operational metrics, alerts, redaction tests,
    and runbook steps without logging PII or secrets.

### Phase 3 — P2 performance and documentation

1. **#125 Performance:** measure catalog/query/image behavior first; improve
   pagination, indexes, query count, caching, or image assets only where the
   baseline identifies a bottleneck. Do not introduce a CDN/object store
   without an owner-approved provider.
2. **#126 Load:** create repeatable synthetic load scenarios and measure
   p50/p95/p99, error rate, resource use, and inventory correctness on
   authorized staging only. No production load testing.
3. **#127 Docs:** update README, architecture diagram, API/database/payment,
   Firebase, deployment/rollback, backup/restore, troubleshooting, and privacy
   documentation to match implemented behavior; remove stale production URLs
   and verify no credentials appear.

## Validation strategy

- Before implementation, keep the current baseline results above as reference;
  investigate the two failing tests before deciding whether they are in scope
  or genuine pre-existing defects, and report them explicitly.
- Use TDD for behavioral changes: focused failing test, confirm expected
  failure, implement minimal behavior, rerun the focused test.
- Run narrow tests for each phase, then `npm.cmd run check`,
  `npm.cmd test`, `npm.cmd run test:coverage`, `npm.cmd run predeploy:check`,
  `npm.cmd run build:pages`, OpenAPI validation, and migration/integration tests
  against a dedicated PostgreSQL database when available.
- For secrets, report only aggregate counts, affected paths/refs, and
  redacted fingerprints; never print matched values.
- For external acceptance criteria, preserve an explicit pending/evidence
  checklist: provider rotation/revocation, SePay sandbox/live verification,
  Render staging/production configuration, GitHub branch rules, external backup
  storage/restore, and authorized staging load/E2E runs.

## Risks and mitigations

- **Secrets in history:** scanning output can itself expose credentials. Use
  redacted output and do not include raw matches in artifacts or logs.
- **Monolith refactor:** broad extraction can introduce regressions. Extract
  one route/domain at a time behind existing tests; defer behavior changes.
- **Consent semantics:** optional marketing/service consent must not be confused
  with legally/operationally necessary order fulfillment; define purpose checks
  explicitly and document retention.
- **Payment verification:** account matching and provider sandbox/live contract
  may require provider-specific fields. Keep provider-specific assumptions
  isolated and fail closed.
- **Coverage gate:** 80% across all code may be disproportionate. Apply the
  issue's threshold to a defined set of critical business modules and retain
  existing repository-wide thresholds otherwise.
- **External configuration:** code can validate presence/shape but cannot prove
  secrets are valid or provider services work. Report the exact operator action
  and evidence still needed.
- **Current test failures:** fix only after root cause is confirmed; do not
  weaken assertions or misattribute baseline failures to this work.

## Decisions and remaining implementation calls

- Work directly on the existing `main` checkout, preserving the user's
  previously chosen no-worktree preference. Do not commit unless asked.
- Order work P0 → P1 → P2, with dependency ordering inside each phase.
- Use current Node.js/PostgreSQL/static frontend stack and existing test runner.
- The implementer may choose exact module boundaries, indexes, CSP directives,
  E2E test selectors, and load-test tooling after inspecting existing patterns;
  any new dependency or provider integration must be justified by an issue and
  validated before adoption.
- Keep external operational criteria open until verified by an authorized
  operator; do not close issues merely because repository code changed.
