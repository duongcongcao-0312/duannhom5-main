# Issues #113–#138 Completion Design

## Intent

Complete the repository-controlled work for open GitHub issues #113–#138, preserving existing behavior and adding regression evidence. The user selected the full open-issue scope.

## Current Scope

- Implement open technical issues #113–#123 and #125–#126, #131–#137, in dependency order after verifying prerequisite work outside this range.
- #124, #127, #128, and #129 are closed and will not be reimplemented.
- #138 is a release-readiness checklist, not a feature issue. Its criteria are evidence gates; it must not be marked complete based only on local code or tests.
- #130 explicitly requires a read-only investigation, no file changes, no production calls/migrations, and a stop for user confirmation. Analyze it first and pause the overall batch after delivering the report. Resume other work only after the user responds.
- Preserve all existing staged, unstaged, and untracked work. The current modified files `assets/api-config.js` and `tests/site.test.js` are unrelated in-progress work and must remain intact.
- The GitHub issue bodies are the acceptance source of truth; this design groups execution and records constraints without replacing their criteria.
- Preserve the existing storage model: PostgreSQL for configured production deployments and JSON/file storage for local/demo. Shared production controls must use shared durable storage.
- For #133, preserve guest order tracking with a separate high-entropy order access code, distinct from the UUID. The user selected this over requiring guest users to create accounts. Store only a verifier/hash and require both values for guest lookups.
- Reuse the documented backup targets in `docs/backup-restore-incident-runbook.md` (PostgreSQL 15-minute RPO/60-minute RTO; file storage 24-hour RPO/30-minute RTO). These remain targets until measured in a restore drill.
- Use WCAG 2.2 AA and the issue-defined viewport/browser classes. For load testing, report repeatable measured results and recommendations; do not invent production SLOs absent an agreed traffic target.

## Goals

- Close actionable gaps in the repository with focused changes and tests.
- Use incremental, test-first changes, retaining API compatibility unless an issue requires a documented contract change.
- Clearly separate locally verifiable code from operations requiring provider credentials, infrastructure, production data, or GitHub administration.
- Provide an auditable completion report against the #138 Definition of Done without claiming unverifiable production readiness.

## Non-goals and Safety Constraints

- Do not modify production data, run production migrations, send real payment webhooks, load-test production, or expose credentials/PII.
- Do not rotate provider credentials, create external environments/storage, configure GitHub branch rules, or deploy without authorized access.
- Do not change issue #130 code until the user explicitly confirms after receiving its read-only report.
- Do not reimplement issues already closed.
- Do not treat skipped tests, missing external resources, or failed baseline tests as passing evidence.

## Approaches

1. **Complete all open issues incrementally, distinguishing repository work from operator actions (chosen).** This matches the request, honors #130's stop condition, and avoids pretending external actions have happened.
2. **Implement only P0 issues first.** Lower risk per batch, but leaves most of the explicitly requested work undone.
3. **Claim full release completion from local code changes.** Rejected because several acceptance criteria require real staging, provider configuration, restore drills, branch protection, and reviewed operational evidence.

## Dependency-Ordered Work

1. **#130 read-only diagnostic:** trace admin status update from UI through API and persistence; record confirmed code paths, hypotheses needing Render logs, and focused tests. Do not edit code or contact production. Stop and wait for user confirmation.
2. **P0 security and correctness:** #113 payment webhook/idempotency; #114 session/browser security; #131 shared rate limiting; #133 order privacy/ownership. Verify prerequisites #109–#112 and required #114/#119/#124 dependencies before implementation.
3. **P1 data, quality, and operations:** #115 database transactions/migrations; #116 consent and privacy lifecycle; #117 backup/restore; #118 backend modularization; #119 OpenAPI/API consistency; #120 business/integration testing; #121 Playwright E2E; #122 CI/CD controls; #123 staging/rollback; #132 email/password recovery; #134 accessibility; #135 visual/browser regression; #137 UX states.
4. **P2 performance and discovery:** #125 pagination/query/cache/images; #126 isolated load testing; #136 technical SEO.
5. **#138 release evidence:** reconcile test/build/security/accessibility/performance/operations evidence, list remaining external blockers, and provide a Go/No-Go assessment. No release-ready claim without the required external evidence.

Within each group, inspect existing implementation first and split work into small independently testable changes. Add/update documentation alongside the related implementation.

## External Operator Dependencies

- GitHub account administration for branch protection, environment approvals, repository scanning settings, and updating issue states/checklists.
- Render/hosting access for environment variables, staging, deployment, health checks, and rollback drills.
- SePay sandbox/provider authorization for payment reconciliation and end-to-end webhook verification.
- Dedicated PostgreSQL test/staging resources for migration and transaction acceptance.
- Email-provider credentials and verified sender configuration for end-to-end delivery.
- Independent encrypted backup storage and an isolated restore target for backup/restore drills.
- Isolated staging capacity for load testing and real browser/device matrix review.

These remain explicitly blocked until authorized access/resources exist; local configuration, mocks, or documentation alone do not satisfy their production acceptance criteria.

## Verification

- Every behavior change follows a red-green regression-test cycle.
- Run the narrow relevant tests after each change, then the complete project test suite and syntax/build checks.
- Report existing unrelated failures by test name and distinguish them from regressions.
- Validate migrations only against disposable/test databases.
- For browser, accessibility, visual, and load checks, record the tested tools, browser/viewport/load profile, and outcomes; do not infer coverage from static checks.

## Decisions and Pause Gates

- Guest order access uses the user-approved order access code described above.
- Implementation choices not fixed by issue acceptance will follow current repository patterns, fail safely, and be recorded with the related change.
- Work must pause after #130's read-only report pending the user's confirmation.
